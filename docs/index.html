Replacing MIXMAX speeds up Geant4 by 2–9% on one thread and 3–14% on 96

Sebastiano Vigna Università degli Studi di Milano

Geant4 11.4.3, five workloads, on a 96-core AMD Zen 5 server (clock fixed at 4.5 GHz). With MWC192X called through an inlined, non-virtual path, every workload runs faster than stock; xoshiro256++ follows, up to two points behind (four on testem11 with 96 threads, where its jump costs most). The physics is unchanged: every observable agrees across engines, and the same engine and seed give identical results in every build.

Only generators that produce a number in 1–2 ns and support jumping are considered, so that, as with MIXMAX, distinct seeds give non-overlapping streams: MWC192X and xoshiro256++. The author designed MWC192X and co-designed xoshiro256++.

The gain has two sources, and they add up

The engine. Swapping the engine behind Geant4's existing call (drop-in, chosen at run time, same binary) saves the generator's own cost: cheaper draws and, in multithreaded runs, a far cheaper reseed. Geant4 reseeds each worker's engine at the start of every event; MIXMAX takes 23 µs to do it on this machine, xoshiro256++ 6.6 µs, MWC192X 0.5 µs. That is why testem11, whose events are short, gains 12% on 96 threads but 2% on one thread, where it reseeds once per run.

The call path. Stock G4UniformRand() calls the out-of-line HepRandom::getTheEngine() through the PLT, then the virtual flat(). The fast path reads a thread-local pointer and calls the engine class chosen at build time directly, inlined. It helps every engine, MIXMAX included: up to 6% on opnovice2, which draws 160 000 numbers per event, nearly all through G4UniformRand().

Where the time goes

The microbenchmark below times one call in a tight loop on one core. That loop runs at 5–7 instructions per cycle and overlaps successive calls, so its time per call understates what a draw costs inside a simulation. Hardware counters on the real workloads agree with it on the instructions saved, not on the cycles: in situ, drop-in MWC192X saves about 8 cycles per draw over MIXMAX, where the loop shows no saving at all. The measured gains therefore exceed predictions computed from draw counts and the microbenchmark.

Reseeding is the exception: it is a long, serial computation whose cost the microbenchmark measures faithfully. With 96 threads a testem11 event takes about 264 µs of thread time, so MIXMAX's 23 µs reseed is about 9% of it, which the cheap-seeding engines save almost entirely. Both engines are seeded by jumping, so distinct seeds give non-overlapping streams, as with MIXMAX.

A production change needs much less than the study did. Geant4 already accepts any engine through G4Random::setTheEngine; the one gap for the drop-in is that worker threads clone the master's engine from a hard-coded list of engine types, a few lines in each of the two thread-initialization files. The fast path adds about 50 lines: G4RngFast.h, two thread-local pointers kept current in Random.cc, and the G4UniformRand() macro. Selection by environment variable, draw counting and the debug hooks are study scaffolding.

Checks, and what to keep in mind

  • Physics. Each campaign compares every observable of every workload across engines (Welch t, family-wise α = 1% by Bonferroni over the distinct comparisons). All passed; the smallest p was 0.016 (testem3 charged steps, xoshiro256++) against a threshold of 0.00038. The same engine, seed and repetition gave bit-identical observables in every build: 660 runs compared on one thread, 300 on 96 threads.
  • Code layout. A comparison between two binaries is called significant only if its interval clears the layout band, the spread measured between two relinks of identical code (0.4–2.1% here). The drop-in getTheEngine() hot path is checked to be instruction-identical to stock, with the same 1019 call sites.
  • Stock vs drop-in MIXMAX should be zero and is, within the band, on four workloads. On opnovice2 stock is 2.1% faster on one thread and 1.0% on 96, just beyond the band. The likely cause is code placement in libG4clhep, the only library that differs on one thread. It makes the opnovice2 figures against stock 1–2 points lower than those against drop-in MIXMAX.
  • Parallel slots. Eleven single-thread runs side by side slow each other by 0.4–0.5% (interval upper ends below 1.01, spread below 1%), equally for every configuration; the 96-thread runs ran alone.
  • The multithreaded timer includes worker run initialization, the same for every engine, which dilutes the 96-thread ratios slightly.
